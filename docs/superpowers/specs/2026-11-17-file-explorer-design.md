# File explorer (channel drives) — design

## Intent
Team members get a Windows-Explorer-like file manager inside Mattermost. Every channel they belong to is a folder with its own **drive**: a file space separate from chat where people upload, organise (sub-folders, rename, move, copy, delete) and preview files, without posting messages. Files already shared in chat are visible there too, read-only. The user wants a friendly, standard Explorer UX: multi-select, rubber-band selection, drag-and-drop upload, context menus, image previews. Later they want to "mirror" one channel's files into another folder; this design keeps that possible but does not build it.

## Goals
- Per-team on/off in Team Settings (`Team.FilesEnabled`), off by default.
- Root: one folder per channel the user is a member of (current team, public + private, not DMs/GMs).
- Inside a channel folder: user-made folders/files (the drive) + a read-only virtual folder **"Chat attachments"** listing every file posted to that channel.
- Operations: upload (button, drag-and-drop of files and folders from the OS), new folder, rename, cut/copy/paste, drag to move/copy, delete to a per-channel **Recycle Bin** (30 days, restorable), download (single file, or several/folders as zip).
- Selection: click, Ctrl+click, Shift+click, rubber-band drag, Ctrl+A, Esc.
- Layout **C** (picked by the user from mockups): left folder tree, toolbar, address bar with breadcrumb + search, main area (Large icons / Details), right **preview pane** for the selected file, status bar.
- Image thumbnails everywhere; double-click opens the existing preview modal.

## Non-goals (v1)
- Mirroring/linking a channel's files into another folder (future; see "Future" below).
- DMs/GMs, cross-team views, global search over drive files, quotas beyond the existing per-file `MaxFileSize`, version history, sharing links, undo (Recycle Bin covers mistakes), posting a drive file to chat.

## Anti-goals
- Anyone seeing a file or folder name from a channel they cannot read, including via guessed ids.
- Explorer actions changing chat history (chat attachments are read-only in the explorer).
- A drive file ending up attached to a chat post, or a chat action silently breaking a drive file.

## Approaches
1. *View over chat* (every action edits/creates posts) — rejected by the user: leaves "(edited)" marks and empty posts in chat; no sub-folders.
2. **Channel drive (picked).** New `DriveItems` table holding folders and file entries per channel; chat attachments shown read-only. Real Explorer behaviour and a natural base for mirroring later.
3. (UI) Classic (A), modern OneDrive-like (B), classic + preview pane (C) — user picked **C**.

## Decided by the user
- Model B (channel drive), layout C, team toggle, members-only visibility.
- Rights: every channel member can upload, create folders, copy and download. Rename, move, delete: anyone on their own items; channel admins, team admins and system admins on everyone's.
- Recycle Bin, 30 days. Uploading to the drive posts no message and sends no notification. Chat attachments read-only but copyable into the drive. Moving/copying across channels only if member of both. Archived channel → drive read-only. A user who leaves a channel loses access; their files stay.

## Design — server

### Team toggle
`Team.FilesEnabled bool` (`json:"files_enabled"`) + `TeamPatch.FilesEnabled *bool`, wired exactly like `DailyReportsEnabled` (`public/model/team.go`; `sqlstore/team_store.go` column list/insert/update). Every drive endpoint first loads the channel and requires: channel has a team, team `FilesEnabled` and not deleted → else 403 `app.drive.disabled.app_error` (same shape as `RequireDailyReportsEnabled`, `app/daily_report.go:26`).

### Data
Migration `000250_create_drive_items` (postgres up/down, plus the entry in `migrations.list`):
- `ALTER TABLE Teams ADD COLUMN IF NOT EXISTS FilesEnabled boolean NOT NULL DEFAULT false`.
- `DriveItems`: `Id varchar(26) PK, ChannelId varchar(26), ParentId varchar(26) ('' = channel root), Type varchar(16) ('folder'|'file'), Name varchar(256), FileId varchar(26) ('' for folders), CreatorId varchar(26), CreateAt, UpdateAt, DeleteAt bigint (0 = live; >0 = in Recycle Bin), DeletedBy varchar(26)`.
- Indexes: `(ChannelId, ParentId, DeleteAt)`; `(ChannelId, DeleteAt)` for the bin; unique `(ChannelId, ParentId, lower(Name)) WHERE DeleteAt = 0` (names are case-insensitive, like Windows).
- Only the top item of a deleted subtree gets `DeleteAt`; its descendants are hidden because an ancestor is deleted (listing a folder only walks live parents, so nothing extra is needed).

`model.DriveItem` with `IsValid` (name 1–255 chars, not `.`/`..`, none of `\ / : * ? " < > |`, no trailing space/dot), store `DriveItemStore` (Save, Get, GetChildren, GetMany, Update, GetTrash, PermanentDelete, GetExpiredTrash), with timer/retry/opentracing layers regenerated by `make store-layers` (or the repo's equivalent).

### Files and access
- Upload: the webapp uses the existing `POST /files?channel_id=<channel>` (FileInfo with `PostId=''`, `CreatorId=user`), then `POST .../drive/items {type:'file', file_id, parent_id}`. The server only accepts a `file_id` whose FileInfo has `CreatorId == session user`, `PostId == ''`, `ChannelId == channel`, and is not already in `DriveItems`.
- Existing download/thumbnail/preview endpoints already allow any reader of `FileInfo.ChannelId` (`api4/file.go:844-854` etc.), so drive files need no change there. Therefore **`FileInfo.ChannelId` must always equal the drive item's channel**: a cross-channel move updates it.
- **Copies duplicate the bytes** (file backend copy of `Path`, `PreviewPath`, `ThumbnailPath` to new paths, new FileInfo). *(My call: existing hard-delete paths — `PermanentDeleteFilesByPost` `app/file.go:1718`, `permanentDeleteUserFiles` `app/user.go:2314` — remove storage without reference checks, so shared storage would leave dead copies. Duplicating costs disk but every FileInfo owns its bytes and every delete is safe.)* `App.CopyFileInfos` is not reused as-is (it checks nothing and shares paths).
- **Guard against attaching drive files to posts:** `SqlFileInfoStore.AttachToPost` (`file_info_store.go:432`) gets `AND NOT EXISTS (SELECT 1 FROM DriveItems WHERE DriveItems.FileId = FileInfo.Id)`. Without it, a user could send a drive `file_id` in `CreatePost` and move it into chat (rewriting `PostId`/`ChannelId`). Check the post-edit file path uses the same store method; if not, guard it too.
- **FileInfo cache:** the local cache layer caches FileInfos by id and only `Upsert` invalidates. Every rename, move (ChannelId change) and soft delete of a FileInfo goes through `Upsert` or explicitly invalidates, so the old channel loses access immediately.
- **Read rule** *(my call)*: same as chat files — `SessionHasPermissionToReadChannel` (members; for public channels also team members, who could join anyway; system admins). The explorer root still lists only channels the user is a member of. An uploader who left a channel can still fetch their own file by id through the existing file endpoints (existing behaviour, unchanged).
- Drive files are never shown in chat file search: they have `PostId=''` and are not bookmarks, so `FileInfo.Search` already excludes them.
- **Data retention / user deletion** *(my call)*: drive files follow the server's policies like any other file — data retention may delete old ones, permanently deleting a user deletes their uploads. Listing joins FileInfo and skips items whose FileInfo is gone or deleted; the hourly ticker removes such dangling file items.

### Permissions (helper `App.DriveCan(rctx, userID, channel, action, item)`)
- Read (list, download, tree): `SessionHasPermissionToReadChannel` on the channel **and**, when `FeatureFlags.PermissionPolicies` is on, `HasPermissionToChannelAction(..., AccessControlPolicyActionDownloadFileAttachment)` (as `getFileInfosForPost`, `api4/post.go:1678-1690`).
- Create (upload, new folder, paste/copy into): read + `PermissionUploadFile` on the channel; channel not archived.
- Modify (rename, move out, delete, restore, permanent delete) an item: create rights + (`item.CreatorId == user` **or** `PermissionManageChannelRoles` on the channel — held by default by channel admins, team admins and system admins (`public/model/role.go`); this is the "admin" test. `PermissionDeleteOthersPosts` would miss channel admins). Folders: a non-admin may delete/move a folder only if every live item under it is theirs; otherwise 403 with a clear message.
- Cross-channel move/copy: read on source (+ modify for move) and create on target.

### API (`/api/v4/channels/{channel_id}/drive`, `APISessionRequired`)
| Method & path | Does |
|---|---|
| `GET /items?parent_id=` | live children (folders first), each with embedded `FileInfo`, plus `path` (ancestor list for breadcrumb). Cap 2000 children; no paging. |
| `POST /items` | `{type:'folder', name, parent_id}` or `{type:'file', file_id, parent_id}` |
| `PATCH /items/{item_id}` | `{name}` rename (also renames `FileInfo.Name` for files) |
| `POST /move` / `POST /copy` | `{item_ids, target_channel_id, target_parent_id}`; whole batch in one transaction; folder copies are recursive. `/copy` also takes `file_ids` for Chat attachments: each FileInfo must have `ChannelId` = this channel, `DeleteAt = 0`, `PostId != ''` or bookmark, and not be burn-on-read (`TemporaryPosts`) |
| `POST /delete` | `{item_ids, permanent}` → Recycle Bin, or permanent (confirmed in UI) |
| `GET /trash` · `POST /trash/restore {item_ids}` · `POST /trash/empty` | Recycle Bin; restore goes back to the original parent, or to root if that parent is gone |
| `GET /chat_files?page&per_page&sort_by=CreateAt\|Size\|Name&sort_desc` | the "Chat attachments" virtual folder (below) |
| `POST /download {item_ids}` | zip of the selection (folders recursive) via existing `App.WriteZipFile` |

- Name clashes on upload/copy/move: auto-rename `name (2).ext`, `name (3).ext`… Rename to an existing name → 400 "A file or folder with this name already exists".
- Moving a folder into itself or its descendants → 400.
- Zip: *shortcut: buffered in memory, capped at 200 MB total (413 above); switch to streaming if people hit it.* Single-file download uses the existing `/files/{id}?download=1`.
- Chat attachments endpoint: `App.GetFileInfos` with `ChannelIds:[id]` and a new `GetFileInfosOptions.ChatAttachmentsOnly` that applies file search's filters (`sqlstore/file_info_store.go:578-582`): `(PostId != '' OR CreatorId = 'bookmark')` and `NOT EXISTS (TemporaryPosts …)` (hides burn-on-read). Add `model.FileinfoSortByName = "Name"` to `GetWithOptions`. Read permission as above.

### Recycle Bin purge
Leader-only hourly ticker (same pattern as daily reports' ticker): items with `DeleteAt` older than 30 days are permanently deleted. Permanent delete removes the `DriveItems` rows of the subtree, soft-deletes their FileInfos (via `Upsert`/invalidate) and removes their physical files (each copy owns its bytes).

### Channel lifecycle
- Archived channel: reads allowed, all writes 403.
- Permanently deleted channel / team: delete its `DriveItems` rows (hook where channel permanent delete already cleans up).
- Leaving a channel: nothing to do; permission checks cover it.

### Websocket
After any write, broadcast `drive_changed {channel_id, parent_ids}` to the channel. Open explorers on an affected folder re-fetch it (and the tree node).

## Design — webapp

### Entry
- Team Settings: "Files" toggle in `team_info_tab.tsx` next to Daily reports.
- Sidebar: "Files" link in `sidebar_list.tsx` next to `DailyReportsLink`, built like `daily_reports_link.tsx`, shown only when `team.files_enabled`.
- Routes in `center_channel.tsx`: `/:team/files`, `/:team/files/:channelName/:folderId?` (`chat` and `trash` are reserved folder ids for the two virtual folders). Toggle off → redirect to the team's default channel. New folder `components/file_explorer/`.
- Client: `Client4` drive methods in `client4.ts` (and Go `client4.go` for tests).

### Layout C
- **Toolbar:** Upload ▾ (files / folder), New folder, Cut, Copy, Paste, Rename, Delete, Download, View ▾ (Large icons, Details), Preview pane on/off. Buttons disable when the action isn't allowed for the selection (e.g. read-only Chat attachments, others' files for non-admins).
- **Address bar:** Back, Forward, Up; breadcrumb `Files › ~channel › Folder › Sub` with clickable segments; "Search this folder" filters the loaded items by name (client-side).
- **Tree (left):** "Files" root → channels (lock icon for private) → lazy-loaded sub-folders; under each channel "Chat attachments" first and "Recycle Bin" last. Items can be dropped on tree nodes.
- **Main area:** *Large icons* (thumbnail via `getFileThumbnailUrl` for images, file-type icon otherwise) or *Details* (Name, Date modified, Type, Size, Uploaded by; header click sorts — client-side for drive folders, server-side for Chat attachments). Folders always first. View choice remembered in localStorage.
- **Preview pane (right):** for one selected file: larger preview (`getFilePreviewUrl` for images, icon otherwise), name, type, size, dimensions (images), uploaded by, date, Open / Download buttons; for several: "N items selected, total size". Auto-hides below ~1100 px width.
- **Status bar:** `N items · M selected (size)`, upload progress summary.
- **Empty states:** empty folder with "Drop files here or use Upload"; empty Recycle Bin.

### Interaction
- **Selection:** click, Ctrl/Cmd+click toggle, Shift+click range, rubber-band drag on empty space (Ctrl adds), Ctrl+A, Esc clears.
- **Open:** double-click / Enter — folder: navigate; file: `FilePreviewModal` with the folder's files as the gallery and no post (header shows file info only).
- **Context menu:** on items (Open, Download, Cut, Copy, Rename, Delete, Properties → preview pane) and on empty space (Paste, New folder, Upload, Refresh, View). Same enable rules as the toolbar.
- **Keyboard:** arrows move focus, Enter open, Backspace / Alt+↑ up, Alt+←/→ back/forward, F2 inline rename, Delete → Recycle Bin, Shift+Delete → permanent (confirm dialog), Ctrl+C/X/V, Ctrl+Shift+N new folder, F5 refresh.
- **Drag inside the explorer:** drop items on a folder (grid or tree). Same channel → move; different channel → copy (like Windows across drives); holding Ctrl forces copy, Shift forces move. Drop target highlights; invalid targets show a no-drop cursor. Dragging from Chat attachments always copies.
- **Drag from the OS:** a full-pane overlay "Drop to upload to ~channel › Folder"; dropping on a folder tile uploads into that folder. Dropped folders are recreated (via `DataTransferItem.webkitGetAsEntry`).
- **Uploads:** existing `uploadFile` action (`actions/file_actions.ts:34`) per file, then create the drive item; bottom-right upload panel with per-file progress, cancel, and errors (e.g. size limit).
- **Delete:** to Recycle Bin without a confirm (Windows behaviour), with a toast "Moved N items to Recycle Bin · Undo" (Undo = restore). Permanent delete and Empty Recycle Bin always confirm.
- **Recycle Bin view:** Details view with "Deleted on", "Deleted by", "Original location"; actions Restore, Delete permanently, Empty.
- **Live updates:** on `drive_changed` for the open folder, re-fetch and keep the selection where items still exist.
- **Accessibility:** grid uses `role="grid"`/`gridcell` with roving tabindex; every action reachable by keyboard and context menu (drag is never the only way: Cut/Paste covers move); names announced; focus visible.
- **i18n:** en + tr. Server strings → run `make i18n-extract`.

## Tests
- **Model:** `DriveItem.IsValid` (bad names, length).
- **Store:** CRUD; children listing hides items under a deleted ancestor; unique name per folder (case-insensitive) among live items only; trash listing; expired-trash query; `ChatAttachmentsOnly` filter (hides unattached and burn-on-read, keeps bookmarks); `Name` sort; `Team.FilesEnabled` round-trip.
- **API:** toggle off → 403; non-member → 403; ABAC download-denied → 403; member uploads/creates folder; non-admin cannot rename/move/delete others' items, admin can; folder with others' files blocks non-admin delete; claim of someone else's `file_id` rejected; cross-channel move updates `FileInfo.ChannelId` and needs membership in both; copy creates new FileInfos with their own storage paths; copying a burn-on-read or other-channel chat file → 403; `CreatePost` with a drive `file_id` fails and leaves the file in the drive; channel admin (not team admin) can rename others' items; after a cross-channel move the old channel's member gets 403 on `/files/{id}` immediately (cache); move into own descendant → 400; name clash auto-rename; archived channel writes → 403; restore to root when parent gone; deleting a chat post doesn't affect a drive copy of its file; zip cap → 413.
- **Webapp:** sidebar link hidden when off; root lists only O/P member channels; selection model (Ctrl/Shift/rubber-band); disabled actions for read-only items; drop overlay calls upload; context menu actions dispatch the right client calls.

## Future (not built)
Mirroring a channel into another folder: add a `DriveItem.Type = 'link'` pointing at a channel/folder, rendered as a folder whose children come from the target; `GetFileInfosOptions.ChannelIds` already supports multi-channel queries.
